# Security Policy

## Scope

Security reports are appropriate for vulnerabilities in repository code, validators, automation, workflows, dependencies, or published executable artifacts that could create a material security impact for users of this project.

A disagreement with a corpus proposition, taxonomy term, evidence requirement, or expected disposition is normally a public issue rather than a security report unless disclosure would expose an exploitable vulnerability or sensitive information.

## Reporting

Do not disclose an unpatched vulnerability, secret, credential, personal data, confidential incident record, or other sensitive material in a public issue or corpus entry.

Use GitHub's private vulnerability reporting facility for this repository when available. If private reporting is not available, contact QBF Consulting through a private organizational contact channel rather than publishing exploit details.

Include enough information to reproduce and assess the problem without including unnecessary sensitive data.

## Corpus incident material

The public corpus is not an incident repository. Cases derived from real incidents must use public sources or be generalised so that confidential, personal, regulated, or security-sensitive information is not disclosed.

A case should preserve the technically relevant proposition and provenance boundary without exposing affected parties or operational details that are not already appropriately public.

## Supported versions

Until a stable release policy is established, security fixes target the current default branch and the most recent tagged v0.x release where practical. Older development snapshots should not be assumed to receive backports.
